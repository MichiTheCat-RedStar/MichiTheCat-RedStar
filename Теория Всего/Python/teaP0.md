## teaP0

**teaP0 - является первым стандартом от меня для языка Python, созданный для структурирования написания кода на Python.**

teaP0 - это совокупность приёмов при программировании на питоне, а именно способ сделать программирование на Python стандартизированным, чтобы каждый файл был ясный и удобно читаемый.

---

### 1. Основы разметки:

Стандарт сделан для подробного и точного описания, чтобы код было удобно поддерживать, вот принципы для программирования на нём:

- Отступы сделаны в виде табуляции, то есть используются нажатия на TAB вместо пробелов, где одно нажатия ТАБ заменяет 4 пробела.

- Разрешено писать `with open(*) as f: f.write(*)` в таком виде, то есть в одну строку, а не две.

- Очень важно, чтобы комментарии не выходили за предел 72 символов строки, иначе их неудобно читать, однако если комментарий относится к мета-контенту, например `#TODO`, то его можно вынести табуляцией за 72 символа, чтобы комментарий было чётко видно отдельно от кода.

- Простые комментарии необходимы, если в коде использована неуточнённая константа, например: `print(a + 1) # 1 - так как люди, в отличие от программы, считают индекс с единицы`, - то есть комментарии используются чтобы объяснить почему именно это значение задано хардкодом.

### 2. Шапка:

Шапкой является код, написанный в начале файла:

```python
# 	<Имя файла> // ☭
# MichiTheCat-RedStar (c) 2026
```

Это обеспечивает единообразие в заголовке. Важно заметить, что в первой строке после решётки идёт сначала пробел, а потом табуляция, чтобы даже если человек открывает файл не по стандарту и у него табуляция равна одному символу, то имя файла было с отступом, относительно АП ниже.

Сразу после шапки, всегда если это возможно, пишется информация с АП для терминала:

```python
print('<Имя файла> - MichiTheCat-RedStar (c) 2026')
print('<Краткое описание>')
```

В блоке `<Краткое описание>` пишется обычно либо описание: "<Имя файла> - это софт для ...", - либо первичная информация для использования: "Для начала работы введите 'help':".

Друг от друга они отделены одной красной строкой:

```python
# 	<Имя файла> // ☭
# MichiTheCat-RedStar (c) 2026

print('<Имя файла> - MichiTheCat-RedStar (c) 2026')
print('<Краткое описание>')
```

### 3. Тело:

Далее идёт две красные строки для отделения контента головы от основного, но тут тоже не всё так просто и код имеет подразделы:

```python
# 	<Имя файла> // ☭
# MichiTheCat-RedStar (c) 2026

print('<Имя файла> - MichiTheCat-RedStar (c) 2026')
print('<Краткое описание>')


# Импорт модулей
<Блоки импорта модулей>


# Основной код
<Основной код>


# TEST
<Тесты>
```

Ниже будет описано подробнее.

#### 3.1 Блоки импорта модулей:

Это могут быть обычные импорты модулей, все импорты должны указывать на конкретную функцию, то есть не допускается писать: `from module import *`, при нужде импорта всех функций необходимо писать `import module`, что позволяет не запутаться из-за пространства имён, а если нужны конкретные модули, то принято писать с указанием функции: `from module import function`.

Сам блок импорта так назван, так как часто это не просто импорт, а блок try-except, в котором находится импорт, обычно это выглядит так:

```python
print('Попытка импорта <Модуль 1>...', end='', flush=True)
try: from <module> import <function>
except ModuleNotFoundError: print('\b'*3, '[Неудачно!]\n'); raise
else: print('\b'*3, '[Успешно.]')

print('Попытка импорта <Модуль 2>...', end='', flush=True)
try: from <module> import <function>
except ModuleNotFoundError: print('\b'*3, '[Неудачно!]\n'); raise
else: print('\b'*3, '[Успешно.]')
```

То есть тут видно, что каждый блок отделён друг от друга.

Так же если есть константы в коде, то они задаются здесь же ниже:

```python
# Импорт модулей
<Блоки импорта модулей>


<ИМЯ_КОНСТАНТЫ_1> = <Значение>
<ИМЯ_КОНСТАНТЫ_2> = <Значение>
```

#### 3.2 Основной код:

Я любитель процедурного программирования, то есть чаще всего тут задаются функции:

```python
def <Имя_Функции_1>():
	<Функция>


def <Имя_Функции_2>():
	<Функция>
```

Функции разделены двумя красными строками, так как внутри функций код может быть разделён одной красной строкой:

```python
def isSpace(chr:str) -> bool:
	if len(chr) > 1:
		raise ValueError('Указано более одного символа!')
	
	if chr == ' ': return True
	else: return False
```

Так же и с классами, они тоже могут иметь подобные отступы внутри для логического разделения функций друг от друга, либо если весь файл хранит в себе только один класс, то вместо отступов функций будут отступы в классе:

```python
class <Имя_Класса>:
	<Функция1>():
		<Функционал>
		
		<Функционал>
	
	
	<Функция2>():
		<Функционал>
```

#### 3.3 Тесты:

Записаны как:

```python
# TEST
if __name__ == '__main__':
	<Тесты>
```

Это сделано для модулей, тут проводятся тесты функций, обычно их вызов и прочее, чтобы проверить работоспособность.

Если же файл является `main.py`, то пишется:

```python
# Точка входа
if __name__ == '__main__':
	<Код>
```

Где код опять же выполнен в императивном стиле с функциями, чаще всего, так как процедурное программирование, но бывают и исключения.

**Вот итоговый пример того, как это выглядит:**

```python
# 	<Имя файла> // ☭
# MichiTheCat-RedStar (c) 2026

print('<Имя файла> - MichiTheCat-RedStar (c) 2026')
print('<Краткое описание>')


# Импорт модулей
print('Попытка импорта <Модуль>...', end='', flush=True)
try: from <module> import <function>
except ModuleNotFoundError: print('\b'*3, '[Неудачно!]\n'); raise
else: print('\b'*3, '[Успешно.]')


<ИМЯ_КОНСТАНТЫ> = <Значение>


# Основной код
def <Имя_Функции>(*):
	return <function>(*)


# Точка входа
if __name__ == '__main__':
	<Имя_Функции>(<ИМЯ_КОНСТАНТЫ>)
```

### 4. Стиль имён:

**Переменные:**

- Булевые: `camelCase`, так как обычно имеют 'is' в начале, например: `isSpace`.

- Константы: `CONSTANT_CASE`, чтобы чётко видеть, что они не должны меняться из кода, например: `API_KEY`.

- Остальные: `PascalCase`, чётко указывает на данные, например: `PlayerInput`.

**Остальное:**

- Атрибуты: `snake_case`, так как не должны привлекать внимание: `test:str=''`.

- Функции: `camelCase`, так как это стиль по-умолчанию, например: `claerScreen();`.

- Классы: `PascalCase`, позволяет видеть классы в коде: `PathTree`.

- Модули: `snake_case`, удобное отображение своих модулей, часто имеют tea* в начале: `teabasic`.

### 5. Мета-пометка:

- Всё описанное здесь было попыткой структурировать моё написание кода и может явно меняться или в реальности выглядеть иначе, например некоторые стили имён могут быть не соблюдены.

- Часто, особенно в маленьких модулях, структура выглядит немного иначе, так как не требует большого программирования.

- Я люблю использовать пространство имён, так как это позволяет понимать откуда какая функция, но это работает не только при ООП, а так же при модулях - я люблю когда есть чёткая структура `имя_модуля.класс.переменная` или подобное, так как это даёт точную информацию без возможности конфликта имён переменных. Так же используется `as` для сокращения пути, если это необходимо.

- Суть этого стандарта записи в том, чтобы давать подробное описание, например полное имя функций, комментарии для хардкод значений и прочее. Из-за этого разрешено нарушение стиля имён иногда для записи в `Hungarian notation`.

- Так же активно используются: `#TODO`, `#FIXME`, `#NOTE`.
